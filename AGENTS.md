# AGENTS.md — music-controller

## Project purpose

Build a **Spotify Car Thing–style media control remote** (HMI) that is **not locked to any one service** (notably not Spotify). First supported backend is **TIDAL**; Spotify / Apple Music / YouTube Music come later, then long-tail sources (browser players, YouTube videos, other streams).

The device is a *controller*, not a player: it displays now-playing metadata and sends transport commands; audio playback happens on the host PC (audio stack) via the service-specific bridge.

## Hardware (target)

- MCU: ESP32-S3.
- Display: 5" capacitive touchscreen, 800×480 (LVGL UI). Planned board: **JC8048W550** (ESP32-S3-WROOM-1: 16 MB flash, 8 MB PSRAM; the vendor's data sheets and demos are not part of this repository, `docs/JC8048W550/` is git-ignored so a local copy can sit there). All UI coordinates assume 800×480.
- Input: rotary encoder — volume adjust (turn), play/pause (click) by default.
- Power: **USB-powered for v1** (battery-powered optional later).
- Connectivity to host PC: WiFi first (the PC connects to the device's WebSocket server); serial (USB CDC) and BLE later.

## Software stack

- UI framework: **LVGL**, the `lvgl/` directory in this repo (vendored as a plain tree, not a submodule), currently **10.0.0-dev** (`build/bin/lvglsim -V`). The code uses its newer setters (`lv_obj_set_hidden`, `lv_obj_set_clickable`, `lv_obj_set_scrollable`); do not assume 9.2 APIs.
- Dev/simulator: this repo's `lv_port_linux` base (SDL2 window, Kconfig-driven, CMake). Used for prototyping the UI.
- Final target: port UI onto ESP32-S3 (ESP-IDF). Treat the Linux simulator as the *reference UI* during development; keep UI code portable (avoid Linux-only calls in `src/music_ui.*`).
- Service bridge: the PC runs the bridge (`bridge/`), which reads the players over MPRIS (tidal-hifi, the TIDAL desktop client, is the 1st target) and connects to the device (the hub) over WiFi.

## Repository layout

Switching animates (`request_layout`): the cover glides/scales, the rest fades out, is rearranged and fades back in (~0.4 s). LVGL gestures (swipes) did not fire reliably from simulated mouse drags, hence the tap. Pure LVGL, no networking; fed through `music_ui_update`, `music_ui_set_lyrics*`, `music_ui_set_album_art_*`; reports button presses via `music_ui_set_transport_cb`, progress-bar seeks via `music_ui_set_seek_cb`, and shows only the transport controls the service reports (`music_ui_set_capabilities`; the flags are in `media_source.h`).

In the LYRICS layout it takes the lyrics panel's place: a round list button at the bottom right of `music_ui` opens/closes it (opening forces the LYRICS layout; tapping the cover closes it; `lyrics_available`/`no_lyrics` keep the LYRICS layout while it is open). The button shows while `MEDIA_CAP_BROWSE` is set (`music_ui_set_capabilities`). `src/browse_worker.*` — the browse thread: the panel's requests (open/play/thumbnail) go to a `BrowseSource` (`media_source.h`, separate from `MediaSource`: listing is slow and must not delay the now-playing poll), results come back through `media_post_to_ui`; after playing an item it re-reads the queue 700 ms later. `MusicAppDeps::browse` hands the source over; `media_browse_mode_t` (`media_poller_start`) decides the capability bit: NONE clears it, WHEN_REPORTED keeps what the source reports, ALWAYS forces it. `src/fake_browse.*` — simulator-only canned `BrowseSource` (`lvglsim -F`, forces the button on), no effect on the real player; it is the only `BrowseSource` so far. A prototype of that backend (PKCE login, token store, playlists/tracks/queue/`play_item`) was written but is not part of this tree and was never tested past the login step. Without Premium, playlists simply do not work; a no-API alternative (a bridge-side recent-plays list replayed through MPRIS `OpenUri`) was considered and not built.

Tapping the "Connection lost" banner opens it directly; long-pressing (0.8 s) the cover opens a **menu** first (`settings_ui_open_menu`: square tiles, `make_tile`/`layout_tiles`: Player = the quick player choice with the current one under the name, Settings). Access: a 16-character shared token (`auth.rs`) is required on every request unless the bridge is bound to loopback (`--no-auth` / `--token X` override; the token is created on first run in `~/.config/music-bridge/token` even when it is not enforced, and shown on the settings page; plain HTTP, so it is not protection against sniffing). Linux only so far (GSMTC for Windows is the next backend); GUI: a **settings page** at `http://127.0.0.1:<port>/` (`ui.rs` + `ui.html`, plain HTML/JS, no external assets) and a **tray icon** (`tray.rs`, `ksni` = StatusNotifierItem, so KDE / GNOME+AppIndicator; menu: status line, Open settings, Quit; `--no-tray`; without a tray host the bridge just runs). The page lists the devices (found over mDNS, pair, remove) and, for the older pull mode, the LAN address to type on the device, the token (hidden by default, copy / regenerate), when a device last called and how many calls were refused for a wrong token (the PC-side answer to "wrong token or wrong address?"); that older-mode block is folded to one line while the bridge listens on this PC only and no device has called, the players with a selector and a "send to devices" checkbox each (`disabled_players` in the config: a switched-off player is set aside in `Hub::snapshot` before the selection is settled, so it is missing from the player list, the states, Automatic and the commands — devices and `/v0` get `no_player` for it —, and the page lists it, greyed, even while it is not running; `POST /ui/players/enabled`), the tidal-hifi supplement (address, reachable, off switch) and listen address/port. It only serves the PC itself (`ui::guard`: loopback peer + loopback `Host` against DNS rebinding + `X-Bridge-UI` header on writes against cross-site posts); `/v0` keeps the token rules. Settings persist in `~/.config/music-bridge/config.json` (command line > file > defaults; the page stores listen address and port only when they differ from the defaults `127.0.0.1:18801` in `config.rs`, so a changed default still reaches everyone who never chose a value); tidal-hifi changes apply at once, bind/port after a restart. Player ids derive from `DesktopEntry`/`Identity`, never the bus name (tidal-hifi's is `chromium.instance<PID>`). KDE Connect phones show up as players (`service: "other"`). ## Build / run (simulator)

- Needs libturbojpeg (pkg-config), libwebsockets (the hub's WebSocket server), nlohmann_json, SDL2.
- `cmake -B build && cmake --build build -j`, then `build/bin/lvglsim` (the hub on port 18322; `-h` lists the options). The generator does not matter (an existing `build/` may be Unix Makefiles or Ninja), so use `cmake --build`, not `ninja`. The project is **C++23** (`CMAKE_CXX_STANDARD`), the firmware too, so that one source means the same on both.
- Changing a `.incbin`-embedded font is tracked via `OBJECT_DEPENDS`; if a font change does not show up, re-run cmake.

- Install the bridge for the current user (Linux): `tools/install_bridge.sh` (release build, `~/.local/bin/music-bridge`, systemd user service started at every login, restarted 3 s after a crash; `--status`, `--uninstall` (keeps the settings and the cache; `--uninstall --purge` deletes them too after a question, `--yes` skips it), `--dry-run`, `--no-autostart`). The bridge takes its port first, so a second copy only says "already running" and exits with code 0.

## Official TIDAL API constraints (do not fight them)

- Official OpenAPI (`tidal-music.github.io/.../tidal-api-oas.json`) has PlaybackState / PlayQueue endpoints, but they require `r_usr`/`w_usr` scopes and `required-access-tier: INTERNAL` (TIDAL first-party only).
- Therefore external apps **cannot** read/control TIDAL "now playing" via the official API. We bridge through the local tidal-hifi API instead. See `docs/tidal-hifi-swagger.json`.

## tidal-hifi's HTTP API (used by the bridge's TIDAL supplement, `bridge/src/tidal.rs`)

Base URL: `http://<host>:47836` (port fixed by tidal-hifi; the bridge's `--tidal-hifi host[:port]`). The device does not talk to tidal-hifi at all.

Read now-playing:
- `GET /current` → `MediaInfo`:
  - `title`, `artists` (a **joined string**; `artistsArray` has the list), `album`, `status` (`playing`/`paused`/...),
  - `current`, `currentInSeconds`, `duration`, `durationInSeconds` (whole seconds),
  - `playingFrom`, `url`, `image`/`icon`, `localAlbumArt`,
  - `favorite`, `player: { status, shuffle (bool), repeat ("off"/"all"/"single") }`,
  - `audioQuality: { quality, badgeText, bitDepth, sampleRate, codec }`.
- `GET /health` for connection status; `GET /current/image`, `GET /current/audio-quality` for details.
- Covers: `/current/image` serves a file tidal-hifi rewrites after the metadata changes, so while skipping tracks it lags or returns an in-between track's art (and is labelled `image/png` while being JPEG); the `image` URL from `/current` is the reliable one (swap `1280x1280` for `640x640`).
- Metadata can be briefly inconsistent after a track change (e.g. new `url` with old `title`); key anything derived from it on all fields, not just `url`.

Playback control:
- `POST /player/next`, `/player/previous`, `/player/play`, `/player/pause`, `/player/playpause`,
- `POST /player/shuffle/toggle`, `/player/repeat/toggle` (repeat cycles off → all → single),
- `PUT /player/seek/absolute?seconds=N`, `/player/seek/relative?seconds=±N` (query parameter, no body),
- `PUT /player/volume?volume=0.5` (0.0–1.0, query parameter, no body).
- Legacy `GET` variants exist (`/next`, `/play`, etc.) but prefer `POST`.
- The swagger summary of `/player/shuffle/toggle` ("Play the previous song") looks like a copy-paste error.

Polling: tidal-hifi exposes no SSE, so `/current` has to be polled (≈1 KB, <1 ms locally).

## Lyrics (implemented)

- TIDAL lyrics are INTERNAL-tier → fetched from **LRCLIB** (`https://lrclib.net/api`, no auth, user-agent set, requests only on track change).
- Lookup (`bridge/src/lyrics.rs`, on the PC): candidates = exact `GET /get?track_name&artist_name&album_name&duration` + free-text `GET /search?q=<title without "(feat…)"> <first artist>` (finds entries filed under another title form, e.g. "あぶく - Bubble"). We score them ourselves: length within 5 s (closer is better), synced lyrics, original script (kana/Hangul/Han ≥ 50 % of the text, so romanized versions lose), album match, exact-lookup bonus; penalty for remix/live/karaoke/… tags the playing title lacks; instrumental entries and synced lyrics whose timestamps run past the track length (a different edit) are skipped.
- HTTP 429 is retried with backoff; the device debounces requests by 500 ms and drops an answer as soon as the track changes; the bridge cancels an older lookup when a newer request comes.
- Parsing keeps timing-only LRC lines as "gap" entries and appends an estimated end marker after the last line, so the highlight clears in interludes and after the song's last line; the UI shows each gap as one blank line (consecutive gaps share it). Unsynced lyrics are shown as a scrollable text.
- **Where the lookup runs:** on the PC (`bridge/src/lyrics.rs`, with a disk cache in `~/.cache/music-bridge/lyrics/`: found lyrics are kept; "none" is believed for one hour only, and an answer where a request was lost with no candidate at all is an *error*, not "none", and is not stored; a lookup that came back empty or failed is repeated once after 2 s; failures are logged as `lyrics: ...` warnings), one lookup at a time; `MUSIC_BRIDGE_LRCLIB` points it at another server for tests, `music-bridge --lyrics-test <title> <artists> <album> <seconds>` prints a result as JSON and `--lyrics-test-full` runs a lookup through cache and retry. The device just receives the finished line list (`MediaSource::lyrics_provider()` → `HubSource::request_lyrics`, so the ESP32 needs no HTTPS); a source without the `lyrics` feature means no lyrics. There is no lookup code on the device. The bridge's unit tests (`cargo test`) cover parsing, the end marker and the ranking.
- UI: 28 px Bold, current line white (color eases, view glides to it), edges fade out instead of clipping, position interpolated between polls, view follows seeks (to the next line, or the last line once the lyrics are over). The current line deliberately keeps the same font size as the others.
- Open questions: standardize on LRCLIB for all services or per-service providers; offline caching on the device.

## Service abstraction (roadmap)

Tier 1: TIDAL (local bridge).
Tier 2: Spotify, Apple Music, YouTube Music (each needs its own host-side bridge / official API).
Tier 3: browser players, YouTube videos, generic streams (likely a browser extension/companion that posts now-playing).

UI/service code should depend on a common normalized `MediaInfo`-like model, not on tidal-hifi JSON directly.

**Adding a service** = one class implementing `MediaSource` (fill `MediaInfo`, map the commands, report `capabilities()`), created in `main()` / `app_main` and passed to `music_app_start()`. Nothing in the UI or poller changes. Per-service flash/RAM cost is small (tens of KB of code; the big buffers — cover, background, JPEG decode — are shared), so prefer one host-side bridge that normalizes several services into one protocol over per-service OAuth/TLS code on the ESP32. Capabilities reach the UI: unsupported controls are hidden (`music_ui_set_capabilities`, called by the poller at startup; without MEDIA_CAP_VOLUME the encoder/volume path is inert).

**Hub (first version implemented in the simulator; see `docs/HUB_PROTOCOL.md`):** the device becomes the hub — sources (the PC bridge) find it over mDNS and connect to a WebSocket server on it, pair once with a code shown on the device, push player state on change and receive commands/cover/lyrics requests over the same socket. The design goal is that the ESP32 is the center (it owns the connection point, the selection and the trust list; several PCs can connect at once; no incoming-firewall rule on the PC). MVP platforms: Windows and Linux. The device is hub-only: it has no client that pulls from the bridge's `/v0` or from tidal-hifi. Try it on one PC: `build/bin/lvglsim`, then `cd bridge && cargo run` (the bridge's own server defaults to `127.0.0.1:18801`, so the two do not clash; add `--device 127.0.0.1:18322` if mDNS does not find the hub), open Settings > Sources > Pair a source on the device and type the code on the bridge's settings page (`http://127.0.0.1:18801/`, Devices). Ports: hub 18322, bridge 18801, both below Linux's ephemeral range (32768-60999) so an outgoing connection of another program cannot hold them; tidal-hifi's 47836 is that app's own. `HubSource` (`src/hub_source.*`, portable core) presents all connected sources to the poller/UI as one `MediaSource`: the poller's 500 ms "poll" only reads the last pushed state (position interpolated), commands go out as `cmd` frames, covers come back as binary frames; focus is the player pinned in Settings > Player (`<source id>/<player id>`), or in "Automatic" the one a source proposes — each source sends its own pick (`players.selected`: the choice made on the PC's settings page, else what plays there) and of the proposals that are playing the one that started last wins, so a browser video does not take over from a player picked on the PC. Paired sources and their secrets are in the device settings (`hub_sources`, mode 0600); the bridge keeps its secrets in `~/.config/music-bridge/config.json` (mode 0600). `src/platform/ws_server.h` is the interface the ESP32 must implement with `esp_http_server` (WebSocket) + the `mdns` component; the simulator uses libwebsockets (for example `pacman -S libwebsockets` on Arch). mDNS: the hub announces `_musicbridge._tcp` (`platform/mdns.h`; simulator = own responder `platform_sim/mdns_responder.cpp`, ESP32 = the `mdns` component; announces on start, goodbye on SIGINT/SIGTERM) and the bridge browses it (`discovery.rs`, `mdns-sd`): known devices are followed by `device_id` when their address changes, new ones appear under "Found nearby" on the bridge's settings page. Lyrics come from the source too (`lyrics_req`, see Lyrics below). Not done: TLS. The ESP32 implementations of the two interfaces exist (`ws_server_esp.cpp`, `mdns_esp.cpp`) but have not run on a chip. Mobile sources are explicitly out of scope for now. Current status, known issues and the prioritized to-do list: `docs/ROADMAP.md`.

## Encoder UX (default)

- Turn: volume up/down. Implemented as `media_poller_volume_step(delta)` (2 % per step, thread-safe, coalesced to one volume command per 80 ms, optimistic target that falls back to the polled `volume` after 2 s). **No volume UI on purpose** (the TIDAL mobile app has none either). The simulator feeds it from the mouse wheel (up = louder) and Up/Down arrow keys via `install_volume_input()` in `main.cpp`; the device's encoder driver should call `media_poller_volume_step()` directly.
- Click: play/pause.
- The UI flips play/pause, shuffle and repeat icons optimistically and ignores the reported values for up to 2 s until they agree.
- Long-press on the cover opens the menu (Player, Settings); touch gestures for skip / seek are still TBD.

## Conventions for edits

- LVGL API is the 9.x/10.0-dev style (`lv_screen_active`, `lv_obj_get_child`, `lv_obj_set_hidden`, etc.).
- `music_ui_create()` is the single UI entry point (extern "C"); it is called by `music_app_start()` (which also builds the settings page and starts the poller) — `main.cpp` only calls `music_app_start()`.
- Keep UI functions pure LVGL; no HTTP/blocking calls on the LVGL thread. Run transport/polling in a separate task/thread.
- **Never call LVGL (including `lv_async_call`, which creates a timer) from a background thread.** Post closures to the mutex-protected queue in `media_poller.cpp` (`post_to_ui`); a 20 ms LVGL timer runs them on the LVGL thread.
- `lv_obj_clean()` / deleting children fires scroll events while it runs: drop your own references to the children first (see `lyrics_clear_labels`), or the handler will touch deleted objects.
- Use the dedicated LVGL 9 setters (`lv_obj_set_scrollable`, `lv_obj_set_hidden`) — `lv_obj_add_flag`/`remove_flag` are deprecated here.
- LVGL's `anim_duration` for scrolling labels is the *total* travel time; derive it from text width for a constant speed (see `TITLE_SCROLL_PX_PER_S`).
- Fonts: text uses Noto Sans KR via LVGL TinyTTF from data embedded with `.incbin` (Regular for UI, Bold for lyrics; glyphs: Latin, kana, Hangul, ~7k Han from KS X 1001 + JIS X 0208, no simplified-only Chinese). Times use the generated mono bitmap font. Both subsets are the KR face, so Japanese kanji show Korean glyph variants.
- JSON uses `nlohmann/json`; JPEG, the WebSocket server, mDNS, settings and WiFi go through `src/platform/` (simulator implementations in `src/platform_sim/`, ESP32 ones in `firmware/components/music_platform_esp/`). Keep OS includes (`turbojpeg`, libwebsockets, ESP-IDF) out of the core files (`music_core` target); new OS dependencies get an interface in `src/platform/` first.
- Formatting: the repository's `.clang-format` for C++ (also for the firmware files), `cargo fmt` for the bridge, and the bridge stays clippy-clean. `tools/format_check.sh` checks all three (part of `run_checks.sh`), `--fix` rewrites. The whole tree was formatted once; those commits are in `.git-blame-ignore-revs`.
- Update `docs/tidal-hifi-swagger.json` if tidal-hifi version changes.
- When a test starts background processes (simulator, bridge, Xvfb), stop them by PID: `pkill -f` matches the shell that runs it, and a leftover simulator keeps its port (a stale `lvglsim -S` once blocked the hub's port).

## Known constraints / do-not-do

- Do not attempt to use the official TIDAL OpenAPI for now-playing or control (INTERNAL tier).
- Do not block the LVGL main loop with synchronous HTTP, and do not touch LVGL from other threads.
- Do not ship hardcoded host IPs: sources find the device over mDNS (the bridge's `--device host:port` is the manual fallback).
- Do not hammer LRCLIB (it rate-limits with HTTP 429): at most one lookup (≤2 requests) per settled track. The only repeat is after a lookup that FAILED (not one that found nothing): the bridge repeats once after 2 s, and the device asks again after 8, 30 and 90 s while the same track plays (`LYRICS_RETRY_AFTER_S` in `media_poller.cpp`; `Lyrics::failed` tells failure from "none"). While a retry is still to come the layout stays and the lyrics area shows "Retrying lyrics..."; the big-cover layout (`music_ui_set_no_lyrics`) comes only when the track has no lyrics or the last retry failed.
